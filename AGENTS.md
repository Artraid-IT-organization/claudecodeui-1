# Repository guidance

## Backend code

For every task that creates, modifies, refactors, or reviews backend code under `server/`, load and follow `$backend-module-standards` from `.agents/skills/backend-module-standards/SKILL.md`. Apply it only to backend code; do not impose those architecture rules on the frontend.

## Вид ленты ответов (`src/components/chat/view/subcomponents/Markdown.tsx`)

Три грабли, каждая стоила отдельной выкатки «ничего не изменилось»:

1. **Уровни заголовков сдвинуты.** `#` рендерится в `<h2>`, `##` — в `<h3>` и так
   далее: в документе остаётся один `h1`. Правила вида `.prose h1` в `index.css`
   промахиваются мимо и выглядят как рабочие.
2. **Размер заголовка задаётся в компоненте, не в CSS.** Utility-классы Tailwind
   (`text-[22px]`) лежат в слое выше `components`, поэтому `index.css` их не
   перебьёт. Меняешь кегль — меняй класс в `Markdown.tsx`.
3. **Абзац — это `div`, а не `p`,** и подзаголовок отличается от жирного слова
   только классом `md-subheading`, который ставит сам разметчик. Чистым CSS их не
   различить: `:only-child` считает теги и не видит текст вокруг, поэтому целился
   и в `текст <strong>слово</strong> текст`, разрывая абзац.

Правка вида проверяется снимком отрисованного элемента с ЖИВЫМ CSS с сервера, а
не `grep`'ом по `dist` — обе прошлые ошибки прошли проверку файлами.

## Изоляция веб-пользователей: смотреть на КАЖДЫЙ рождающийся процесс (12.09.26)

Разделение аккаунтов делалось дважды и оба раза оказывалось неполным, потому
что проверялось только чтение данных — чьи чаты видно в списке. Но у сервера
есть второй, куда более опасный канал: процессы, которые он запускает от имени
пользователя.

Встроенный терминал (`shell-websocket.service.ts`) отдавал оболочке
`...process.env` целиком и вообще не получал опознанного пользователя —
websocket-шлюз передавал запрос чату, но не терминалу. Значит `CLAUDE_CONFIG_DIR`
был серверный, то есть общий каталог владельца площадки. Приглашённый набрал
`/login` — и OAuth-вход владельца был перезаписан чужим. Владелец при этом
увидел не ошибку, а тихую смену аккаунта; приглашённый — «CLI не
аутентифицирован», потому что интерфейс спрашивал про ЕГО каталог, где пусто.

**Правило.** Любое место, где рождается дочерний процесс (`pty.spawn`,
`child_process.*`, SDK с параметром `env`), обязано получать каталог настроек
и ключ из `shared/web-user-runtime.ts`, а не из окружения сервера. Если
пользователя определить не удалось, а `OPEN_REGISTRATION` включён — процесс не
запускается вовсе: молча писать в чужой каталог хуже, чем отказать.

**Второе правило, из той же истории.** Расчёт «чей это пользователь и куда ему
можно писать» существует ровно в одном экземпляре. Копия этого расчёта в чате
жила отдельно и не знала про терминал — та же болезнь, что у двух разошедшихся
сверок ленты сообщений в тот же день: копия отстаёт молча, и найти это можно
только по жалобе человека.

## Группы чатов и архив в шапке (13.09.26)

- На месте переключателя пресетов в шапке — `ChatGroupSelector`: «В архив» первым пунктом, ниже группы свежие сверху, галочка у текущей. Порядок задан Егором, не переставлять. Пресет включается во вкладке настроек «Пресеты».
- Хранилище: `chat_groups` (по `account_dir`, как и чаты) + колонка `sessions.group_source`. Имя группы копируется в `group_label` — по нему список слева рисует заголовки без второго запроса; переименование группы обязано обновить копии.
- `group_source='manual'` (в т.ч. «без группы» = manual + NULL) автоматика не пересматривает никогда. `auto` пересматривается при каждой сборке события `session_upserted` (смена названия). Группы старой кнопки «Organize by topic» (`group_id` без источника) не трогаются.
- При общих словах выигрывает старшая по созданию группа — новая не перетягивает чаты.
- Архив из шапки убирает чат из списка слева (`removeSessionFromList`), но не уводит со страницы; `session_upserted` для архивных не рассылается, поэтому убирать приходится на клиенте.
- `ActionMenu` c `portal`: слушатель прокрутки окна висит с перехватом — прокрутку внутри самого меню он обязан пропускать, иначе длинный список закрывается при попытке листать.

## Черновик в поле ввода принадлежит чату (13.09.26)

Ключ `draft_input_<scope>`, где scope — id чата, а у нового чата до первой
отправки — `project:<projectId>` (`draftScopeFor` в `chat/utils/chatStorage.ts`).
Раньше ключ был по проекту и подменялся только при смене проекта, поэтому
текст ехал за человеком из чата в чат одного проекта.

В `useChatComposerState` эффект СОХРАНЕНИЯ черновика обязан стоять выше эффекта
ПОДМЕНЫ и сверяться с `draftOwnerRef`: в кадре переключения область уже новая, а
`input` ещё старый — без сверки текст чата А пишется в чат Б. Отправка стирает
черновик той области, откуда отправили (`submitDraftScope`), а видимое поле —
только если человек всё ещё в том чате: пока грузятся вложения, он мог уйти.
Старые черновики по проекту один раз переезжают в открытый чат
(`adoptLegacyProjectDraft`).

## Чаты переживают перезапуск сайта (13.09.26)

- Агент — дочерний процесс сервера. У службы `KillMode=process` (drop-in `99-keep-agents.conf`), но этого мало: при штатной остановке SDK на `process.exit` шлёт SIGTERM всем своим детям. Проба: штатная остановка родителя — агент погиб; SIGKILL родителя — агент доделал задачу.
- Поэтому агент запускается через `spawnClaudeCodeProcess` → `survivor-runs.js`: во время остановки `kill` — пустая операция; запись `~/.cloudcli-shared/live-runs/<pid>.json` (чат, номер разговора, каталог аккаунта).
- После старта `adoptSurvivors` усыновляет живые записи (PID жив И в cmdline есть `claude` и `stream-json`): реестр считает чат работающим (второй запуск в тот же чат отклоняется), изменения файла переписки рассылаются `session_upserted` с `detachedRun: true` (страница перечитывает переписку даже у «работающего» чата), по завершении — `chat_subscribed isProcessing:false` всем вкладкам. «Стоп» — SIGTERM процессу.
- `useChatSessionState` не перечитывает переписку, пока чат `isProcessing`. Поэтому по завершении пережившего агента порядок строго: сначала `complete` (НЕ `chat_subscribed isProcessing:false` — его вкладка отбрасывает через `ifStartedBefore`, если после подписки отметила чат работающим), потом (через 1,5 с) `session_upserted`. Промежуточные шаги такого агента во вкладке живьём не видны — появляются разом, когда он закончит.
- `jsonl_path` у чата, начатого с сайта, заполняет периодический обход файлов — минуты спустя. История (`claude-sessions.provider.ts`) при пустом пути ищет файл по номеру разговора в папке аккаунта запроса и сразу запоминает путь (`setJsonlPathIfMissing`); без этого открытая вкладка перечитывала пустую историю и не показывала ответ.
- Первая выкатка этой правки идёт поверх старого кода: штатный перезапуск убьёт работающие чаты. Без потерь — только SIGKILL главного процесса (служба сама поднимется: `Restart=on-failure`).


## Метка работы на живых событиях (13.09.26)

`seq` у каждой работы (`chatRunRegistry.startRun`) свой и начинается с 1, а
вкладка отбрасывает события с `seq <= lastSeqRef[sid]` — защита от повторной
доставки. Счётчик был по ЧАТУ и не сбрасывался между работами: после долгой
работы вкладка помнила большой номер и молча выбрасывала ВСЕ события следующей,
включая сигналы «думает / работает». Сервер при этом считал чат занятым.

Теперь каждое событие несёт `runStartedAt` (время запуска работы), его же
возвращает `chat_subscribed`. Клиент (`chat/utils/liveRunCursor.ts`) при новой
метке обнуляет счётчик чата; подписка передаёт известную метку, и сервер при
несовпадении досылает работу с начала. Старая вкладка без метки: если её номер
больше, чем вообще есть у работы, — досылка тоже с начала.

Лента без воды. Размышления в ленте по умолчанию скрыты (`showThinking: false`
в `hooks/useUiPreferences.ts`) — и у тех, кто уже сохранил «показывать»:
одноразовая метка `uiPreferences.thinkingHiddenByDefault.v1`. Текст в размышлениях
ЕСТЬ — первое допущение «они пустые» оказалось неверным и проверялось по записи
разговора (52 блока, пустых 0). Пустые блоки дополнительно не разрывают группу
команд (`isEmptyThinking`). Свёрнутую строку вызова рисует `ToolGroupContainer`
(не `BashCommandDisplay`): в ней `description` вызова, команда — при раскрытии.
Инструмент `Agent` отображается конфигом `Task` (алиас в `getToolConfig`), иначе
падал в «Parameters».

Суб-агент приходит под именем `Task` (старое) или `Agent` (новое). Сравнивать
только через `isSubagentToolName` из `chat/tools/configs/toolConfigs.ts`: жёсткое
`=== 'Task'` в трёх местах (карточка агента, счётчик «Работают агенты», категория
строки) молча отвалилось при переименовании.

## Размышления видны, «думает» заметно (13.09.26, вечер)

- Днём размышления скрыли целиком (v1, жалоба на пустые «Думал N с»). Вечером Егор попросил видеть размышления и «в первую очередь понимать, думает ли чат». Итог: `showThinking` по умолчанию снова `true` (перенос `uiPreferences.thinkingShownByDefault.v2` включает их тем, кому v1 выключил), пустые блоки по-прежнему скрыты `isEmptyThinking`. Не переключать умолчание обратно без слова Егора.
- Текст размышлений приходит только благодаря `thinking: { display: 'summarized' }` в провайдере; в стенограммах текст есть примерно у каждого пятого блока — остальные пустые и не рисуются.
- `ActivityIndicator`: плашка h-10, у каждой фазы свой значок и цвет (`PHASE_ICONS` / `PHASE_TONES`), «думает» — фиолетовый мозг.
- Чат, переживший перезапуск сайта: `src/utils/detachedRuns.ts` помнит такие чаты (по `session_upserted.detachedRun`), и `useChatSessionState` перечитывает их переписку даже во время работы — иначе шаги появлялись разом в конце.
- «Думает» зажигается от `content_block_start` блока размышления: сервер (`claude-sessions.provider.ts`) шлёт пустой `thinking_delta`, клиент ставит фазу `thinking` и до проверки текста. Без этого пересказ размышления приходил одним куском в конце, и всё время размышления плашка писала «Ожидает модель».
- Свёрнутый блок размышлений показывает первые ~90 символов мысли в заголовке (`thinkingPreview` в `MessageComponent`).
- Вкладки открытых чатов (`SessionTabsBar`) получают `processingSessions` и у работающего чата рисуют значок фазы вместо значка Claude (`data-phase` на вкладке). Значки и цвета — общие с плашкой: `chat/utils/activityPhaseStyle.ts`.
- Фоновые вкладки подписаны на живые события своих чатов (эффект в `AppContent`, ключ — набор id вкладок кроме открытой). Без этого после загрузки страницы фоновые вкладки знали только «занят» (список работающих без фазы) и значок висел «ожидает», хотя модель думала. Побочный эффект, как и у открытого чата: подписка переносит живой поток работы на эту вкладку браузера.
- `ChatSessionWriter` шлёт события во ВСЕ подписанные вкладки (`connections`), а не в последнюю. Раньше каждая подписка вытесняла прежнюю: открыл чат на втором устройстве (или страница подписалась на фоновые вкладки, или проверочный браузер открыл чат) — первое устройство молча переставало получать ответ.


## «Ход работы» вместо россыпи строк (13.09.26, поздно вечером)

Лента группирует всё между сообщением человека и текстом ответа (размышления и
вызовы инструментов) в один элемент «Ход работы · N мыслей · M действий»
(`chat/utils/workStretch.ts`, `WorkStretchContainer.tsx`). Образец — webview
Claude Code для VS Code: работа свёрнута, ответ модели и есть отчёт.
Внутри по нажатию: только ключевые размышления (≥ `KEY_THOUGHT_MIN_CHARS`
символов) и шаги через `groupConsecutiveTools`. Не прячутся: текст ответа,
сообщения человека, ошибки, вопросы с кнопками (`isInteractivePrompt`).
Две просьбы Егора, которые это совмещает: «видеть размышления» (плашка «Думает»
и мысли остаются) и «без воды, только нужное». Модели к любому пресету
добавляется `THINKING_LANGUAGE_INSTRUCTION` (chat-websocket) — размышлять
по-русски и только о важном: язык пересказа размышлений идёт за мыслью.
Настройка `showThinking` на ленту больше не влияет — мысли всегда внутри свёртки.

## Честные этапы на плашке вместо «Ожидает модель» (13.09.26, ночь)

- Замер многошаговой задачи: 63% времени плашка писала «Ожидает модель». Проба SDK: ~7 с запуск процесса, ~5 с проверки/настройки до `system init`, ~4 с до `message_start`, после каждого результата команды ~2 с тишины.
- Этапы: `starting` («Запускаю чат» — ставится явно при отправке в `useChatComposerState`), `requesting` («Модель получила запрос» — сервер шлёт `run_phase` на `system init`), `reading` («Модель читает результат» — после `tool_result`). `waiting` остаётся только для чатов с неизвестным этапом (фоновые вкладки, переживший перезапуск).
- `run_phase` — отдельный вид события (`MessageKind` на сервере и в `useSessionStore`), в ленту не сохраняется (`shouldPersist`).
