# Repository guidance

## Backend code

For every task that creates, modifies, refactors, or reviews backend code under `server/`, load and follow `$backend-module-standards` from `.agents/skills/backend-module-standards/SKILL.md`. Apply it only to backend code; do not impose those architecture rules on the frontend.

## Мониторинг подключения MacBook (`server/modules/mac-status`, 19.10.26)

MacBook владельца поднимает SSH SOCKS5-туннель (`ru-exit.command`) → на сервере появляется прокси 127.0.0.1:1080. Модуль `mac-status` каждые 15 с (конфигурируется `MAC_STATUS_INTERVAL_MS`) проверяет SOCKS5, получает через него публичный IP и при смене IP кэширует страну и VPN-классификацию. Статус содержит `connected` и отдельный fail-closed признак `searchReady`: поиск разрешён только при ожидаемой стране `RU` и `isVpn=false`; ошибка внешней классификации оставляет туннель подключённым, но блокирует поиск.

Модуль:

- пишет JSON-статус в `~/.cloudcli/macbook-status.json`;
- отдаёт `GET /api/mac-status` и SSE `/api/mac-status/stream`;
- пушит изменения при смене подключения, готовности поиска или выходного IP, но не на каждую проверку.

Индикатор в шапке (`MacStatusIndicator`) слушает SSE `/api/mac-status/stream` и показывает только точку без надписей: зелёная — российский выход готов (`searchReady=true`), жёлтая — туннель есть, но VPN/страна/классификация не допускают поиск, красная — туннеля нет или актуальность потеряна вместе со связью с сервером. В шапке сайдбара он стоит слева от кнопки обновления в обеих версиях (порядок: MacBook, Refresh, Pulse, NewChat) и неинтерактивен. Подсказка со статусом и причиной блокировки показывается `Tooltip` с `position="bottom"` по наведению/долгому тапу — сверху она уходит за край экрана, т.к. иконка у верхней границы шапки. Внешние поисковые скрипты читают тот же JSON-файл и стартуют только при `connected=true` и `searchReady=true`.

Тесты бэкенда (`server/**/*.test.ts`) не включаются в `dist-server`: `server/tsconfig.json` исключает `**/*.test.ts`, чтобы сборка не требовала dev-зависимостей в окружении без `vitest`.

## Защита выкатки от гонки сборок (`promote-dist-server.mjs`, 16.10.26)

Параллельные чаты собирают `dist-server` из разных worktree/веток и могут молча
выкатить старую сборку поверх новой — чужая правка пропадала без следа
(16.10 антишторм-кулдаун жил в проде ~8 минут, пока чужая сборка его не затёрла).

Теперь каждая выкатка пишет `dist-server/.build-stamp.json`: `builtAt` (mtime
входного `server/index.js`), `promotedAt`, `gitHead`, число dirty-файлов,
путь worktree. Промоут ОТКАЗЫВАЕТ (exit 65), если артефакт кандидата старше
уже выкаченной сборки — протухший артефакт нельзя накатывать поверх нового.
Обход осознанного случая: `PROMOTE_FORCE=1`. Смена `gitHead` при выкатке
печатает NOTE-строку — по ней видно, чьё дерево выкатилось.

Граница защиты: две сборки из разных незакоммиченных деревьев одного возраста
неотличимы — порядок гарантирует `heavy-queue.sh`; метка делает такие выкатки
видимыми (worktree/head в штампе), но не запрещает. Запрет есть только на
доказуемо более старый артефакт.

## Плашка обновлений — жизненный цикл apply-состояния (17.10.26)

Плашка «Обновить» внизу сайдбара управляется тремя файлами в `~/.cloudcli/update-state/`:
`pending.json` (ожидает решения), `apply.json` (ход установки), `dismissed.json` (скрытые).

Состояния `apply.json`: `running` → `ok` | `failed`. Инварианты:

- **Скрипт выкатки** (`deploy/apply-update.sh`) обязан закрыть `apply.json` при любом
  исходе: trap на EXIT пишет `failed`, успешный путь пишет `ok`. Оба через `write_state`,
  которая проверяет `id` и `state === "running"` перед записью — чужое не затирает.
- **Серверный таймаут** (`expireStaleApply` в `updates.service.ts`): при чтении статуса
  сервер проверяет возраст `running` по `startedTs`. Если старше `APPLY_TIMEOUT_MS`
  (45 мин) — переводит в `failed` и пишет файл. Это последний рубеж на случай, если
  процесс выкатки убит без trap.
- **Клиентский таймер** (`ApplyingBanner` в `ServerUpdateSection.tsx`): показывает
  прошедшее время (`useElapsed`). После `CLIENT_APPLY_STALE_MS` (5 мин) появляется
  кнопка «Долго — проверить статус», которая перечитывает `/api/updates/status`.
- **Результат** (`ResultBanner`): после перехода в `ok`/`failed` показывает короткую
  плашку «Обновлено» / «Не удалось», автоскрытие через `RESULT_DISMISS_MS` (15 с).
- **`pending.json` после успешного применения снимается**: `apply-update.sh`
  удаляет файл, если его `id` совпадает с применённым — иначе плашка продолжала
  бы показывать уже вставленную версию (инцидент 18.10.26: после «Обновить»
  оставалось «Обновление · 2 изм.»).
- **Готовая версия (`remote: local-build`) собирается из своей замороженной копии**
  `~/.cloudcli/update-builds/<id>` (`git worktree add --detach`), а не из
  `sourceWorktree` — он только для справки. Рабочая копия чата-автора живёт дальше
  (коммиты, несохранённые правки); 19.10.26 она ушла на коммит вперёд, сверка
  «копия = кнопка» упала — «Не удалось».
- **Устаревшая плашка снимается**: если на сайт уже выкатили то, чего нет в версии
  плашки, `apply-update.sh` отказывает сразу (не после минут сборки), а
  `build-shared.sh` после любой выкатки снимает чужую плашку — вошедшую в выкатку
  (`pending.json.applied-*`) или устаревшую (`pending.json.stale-*` + оповещение в TG).

Граница: клиент не пишет `apply.json` напрямую — только читает через API и может
форсировать перечитывание. Запись — только скрипт выкатки и серверный таймаут.

## Mobile sidebar drawer hides the chat composer

On mobile, opening the sidebar drawer (hamburger menu) overlays the chat. The composer — including the input, activity indicator, permission banner, and queued draft card — is hidden while the drawer is open (`isMobileSidebarOpen` prop) so the input does not stay visible behind the chat list. The composer reappears when the drawer closes. State is preserved because the composer state lives in `ChatInterface`; only the presentational shell unmounts.

The composer keyboard-shortcut hint (`submitHint` in `ChatComposer.tsx`, the "Enter — …" caption between the tools row and the model menu) is not rendered at all on coarse-pointer devices: there is no Enter key to teach and the row never fits the string, so the fit-measurement could show it clipped mid-word. On precise-pointer screens it is still measured by ResizeObserver and hidden via `invisible` when it does not fit whole — do not switch that to `display:none` (oscillation) or re-gate on a viewport breakpoint (the pane width is viewport minus sidebar).

## Живучесть соединения (`WebSocketContext`)

Короткое открытие WebSocket не доказывает восстановление связи: при смене VPN провайдер может пропустить handshake и оборвать поток через 0–6 секунд. Счётчики неудач и нарастающая пауза сбрасываются только после штатного `server_ping`; два соединения подряд без него переключают вход. Для старого сервера без прикладного heartbeat устойчивость подтверждает завершившийся `HELLO_GRACE_MS`.

Нельзя ограничивать подключения общим кулдауном на пользователя: один пользователь штатно держит несколько вкладок и устройств, а отказ нового сокета сам запускает следующий reconnect. Шторм сдерживает клиентский backoff с jitter, не серверный запрет. Переходы `attempt/open/stable/close/reconnect/resume` пишет `connectionProbe.ts` в `[catchup-probe]` с close-кодом, временем жизни и доступным типом сети; максимум 40 записей на загрузку, без текста сообщений.

Самообновление не перезагружает рабочую вкладку автоматически: расхождение сборок, обновление service worker и 404 протухшего asset только очищают старый fallback и показывают «Обновить». Аварийная страница после 4-секундного таймаута тоже не опрашивает сервер и не перезагружается циклом. Перезагрузка — лишь по явному нажатию человека. Лимит в `sessionStorage` недостаточен: `client.navigate()` и fallback-таймер живут вне страницы и на Mac без VPN создавали бесконечные сбросы (инцидент 15.10.26).

Повторная проверка авторизации (`checkAuthStatus`) не демонтирует рабочее приложение: `isLoading` ставится только при первой загрузке (когда `user` ещё нет). Retry при сетевом сбое и token refresh работают в фоне — `ProtectedRoute` продолжает показывать приложение. `checkAuthStatus` стабилизирован через `tokenRef`: refresh токена не пересоздаёт колбэк и не перезапускает effect, иначе каждый refresh демонтировал всё дерево через `isLoading → AuthLoadingScreen` (инцидент 15.10.26, Mac без VPN).

## Service worker перехватывает только своё (`public/sw.js`, 18.10.26)

Воркер — процесс браузера: каждый ответ, который он отдаёт через `respondWith`,
целиком буферизуется в его памяти, а оборванный/бесконечный запрос оставляет
буфер висеть (инцидент 18.10.26 — 5 ГБ и 10% CPU на маке за часы; на iPhone
воркер умирает в фоне, поэтому там это не видно). Поэтому `fetch`-обработчик
обслуживает ТОЛЬКО same-origin GET и только три класса адресов: навигацию
(сеть → «последняя удачная страница» → заглушка; не-ok ответ сервера тоже
уходит в последнюю удачную), `/assets/` и маленькую
статику (`/fonts/`, `/icons/`, манифест, favicon, logo) — обе из кэша.
Новый класс запросов добавлять в перехват только осознанно: POST, чужие домены
и всё прочее обязаны идти мимо воркера.

Навигация идёт через `event.preloadResponse` (navigation preload включён в
activate) — браузер качает страницу параллельно старту воркера; прелоада нет
или он пуст — обычный поход с повтором.

Все `fetch` внутри воркера — с пределом времени (`timeoutSignal`): навигация
45 с, куски сборки 120 с. Запрос без потолка на мёртвой связи держит воркер
живым с накопленным буфером — так он и разрастался. В кэш кладётся только
`response.ok`: ошибка/редирект в кэше = протухший файл навсегда (cache-first
обратной проверки не делает). Статика без хеша в имени — stale-while-revalidate:
из кэша сразу, в фоне перекачивается. Личный манифест `/manifest.json?enter=<токен>`
(содержит логин-токен, сервер шлёт no-store) в кэш не пишется. Любой
`cache.put` — внутри `event.waitUntil`, иначе воркер умирает до записи.
`CACHE_NAME` меняется с каждой правкой файла — purge старых кэшей привязан к имени.

## Потоковая выдача (`useChatRealtimeHandlers`)

Мелкие фрагменты `stream_delta` / `thinking_delta` от WebSocket накапливаются
до следующего кадра отрисовки (`requestAnimationFrame`), а не до фиксированного
100-мс таймера. Это убирает лишнюю паузу при быстром потоке и не даёт куче
фрагментов срастаться в видимый рывок на медленном рендере. При потере
соединения или приходе терминального события накопитель сбрасывается сразу.

**Инвариант границы блока (14.10.26 — дубли ответов в ленте).** Буфер
`accumulated` в `streamingScheduler.ts` держит текст ТЕКУЩЕГО блока целиком:
`flush`/`doFlush` отдаёт накопленное, но буфер не стирает — иначе кадровая
скоуплённость сломается. Стирать обязан `drop(id)` на закрытии блока —
`stream_end` (у Devin он же каждый `tool_call`), `complete`,
`chat_run_started`; для размышлений `flushThinking` зовёт `drop`, не `cancel`
(`cancel` убирает кадр, но текст остаётся и перетекает в следующий блок).
Без `drop` каждая финализация печатает нарастающую копию всего уже показанного
текста — в ленте по 3–7 дублей одного ответа за ход.

## Вид ленты ответов (`src/components/chat/view/subcomponents/Markdown.tsx`)

Служебные `type=error` и `task_notification` в `MessageComponent` всегда занимают одну строку с обрезкой по ширине; ошибка показывает заголовок, время и краткую первую фразу. Тела внешних push/desktop-уведомлений ограничены 120 символами. Полный raw-текст остаётся в данных и серверном журнале. Правило действует на старую историю и новые события всех провайдеров; интерактивные запросы разрешений не сворачивать, иначе человек не сможет ответить.

Три грабли, каждая стоила отдельной выкатки «ничего не изменилось»:

1. **Уровни заголовков сдвинуты.** `#` рендерится в `<h2>`, `##` — в `<h3>` и так
   далее: в документе остаётся один `h1`. Правила вида `.prose h1` в `index.css`
   промахиваются мимо и выглядят как рабочие.
2. **Размер заголовка задаётся в компоненте, не в CSS.** Utility-классы Tailwind
   (`text-[22px]`) лежат в слое выше `components`, поэтому `index.css` их не
   перебьёт. Меняешь кегль — меняй класс в `Markdown.tsx`.
3. **Абзац — это `div`, а не `p`,** и подзаголовок отличается от жирного слова
   только классом `md-subheading`, который ставит сам разметчик. Чистым CSS их не
   различить: `:only-child` считает теги и не видит текст вокруг, поэтому целился
   и в `текст <strong>слово</strong> текст`, разрывая абзац.

Правка вида проверяется снимком отрисованного элемента с ЖИВЫМ CSS с сервера, а
не `grep`'ом по `dist` — обе прошлые ошибки прошли проверку файлами.

4. **Копия выделением — с пустой строкой между абзацами** (25.09.26,
   `utils/copyParagraphBreaks.ts`). Отступ абзаца в буфер не попадает, и в
   Telegram пункты слипались. На время `copy` между выделенными блоками
   верхнего уровня (`[data-md-copy-root]`) ставится `<div><br></div>`, до кадра
   убирается. Буфер не подменяем — пропал бы жирный. После вставки выделение
   ставится заново: Chrome иначе обрывает копию на старом конце выделения.

## Кнопка «В новый чат» на промпт-блоке (проект «Промпты», 19.10.26)

У копируемого блока в чате папки «Промпты» в шапке стоит «→ В новый чат»:
текст блока уходит первым сообщением нового чата ОСНОВНОЙ папки и сразу
отправляется — вместо ручного «выделить, открыть чат, вставить». Признак
«это промпт» — сама папка (`isPromptsProject` в `sidebar/utils/utils.ts`,
путь `/home/claude/prompts` или имя «Промпты»), классификатора содержимого
нет — любой fenced-блок там получает кнопку.

- Механика — тот же слот `pendingHandoff`, что у выжимки handoff: внешние
  постановщики пишут через `queuePendingFirstMessage`/`notifyPendingFirstMessage`
  (`useChatComposerState.ts`), эффект композера подхватывает текст в поле
  нового чата и шлёт обычной посылкой (номер, очередь, защита от потери).
- Целевая папка — `resolveMainChatProject` (общая с кнопкой «Новый чат»
  сайдбара): `/home/claude`, иначе папка с наибольшим числом чатов среза.
- Контекст `RunInNewChatContext` (`{enabled, run}`) провайдится в AppContent
  над MainContent и мемоизирован — без `useMemo` каждый ререндер AppContent
  пересоздавал бы значение и перерисовывал все блоки кода ленты.
- Чат-источник помечается `sessions.prompt_launched=1`
  (`POST /api/providers/sessions/:id/prompt-launched`, идемпотентно,
  вызывается из `runPromptInNewChat` до перехода). Поле проносится во все
  обогащения сессий (`projects-with-sessions-fetch`, `sessions.service`,
  `sessions-watcher`, `chat-run-registry`). В строке чата «Промптов»
  иконка провайдера становится серой (`grayscale opacity-40` в
  `SidebarSessionItem`) — без новых цветов и элементов. Метка независима
  от `is_flagged`/`is_done` и взаимоисключений с ними нет.
- Снимок-проверка: временный экземпляр с `HOME=/tmp/…`, workspace webuser'а —
  симлинк на `/home/claude` (иначе validateWorkspacePath не пустит пути проектов),
  `PLATFORM_OWNER_WEB_USER_IDS=<id>`, креды `.credentials.json` КОПИРУЮТСЯ
  в `.claude-webuser-<id>` (не симлинк — CLI перезаписывает токен при продлении).
- Известный край: нажатие ПОКА блок ещё стримится заберёт неполный текст —
  копия снимается с текущего `raw` в момент клика.

## Картинки в ответах агента — `![alt](…)` в ленте (07.10.26)

- Агент показывает Егору картинку строкой `![подпись](/api/assets/images/<имя>)`
  в своём ответе; файл кладёт в `~/.cloudcli/assets` через
  `~/scripts/chat-image.sh <файл> [подпись]` — скрипт ужимает крупное до
  1600 px и печатает готовую строку (голое имя `shot.png` вместо адреса тоже
  работает). Правило для агентов — ~/CLAUDE.md, блок «Дизайн», п. 5.
- Отрисовка — `MarkdownImage` (`img` в `markdownComponents`, Markdown.tsx):
  адрес хранилища и голое имя → blob с токеном через `useChatImageSrc`
  (`chat/utils/` — вынесен из ChatMessageImages, где лежал раньше; голый
  `<img src>` токен в заголовке не несёт, поэтому не обычный тег);
  `data:`/`blob:`/`https?:` — обычный `<img>`; всё прочее — текст подписи.
  Клик — `ImageLightbox`.
- Картинка едет ФАЙЛОМ: в переписку попадает только строка-имя (~60 байт),
  base64 в историю не лезет — урок чата разбора видео, где 16 МБ кадров
  вытесняли начало переписки (ветка fix/history-heavy-images).
- Хранилище общее на всех веб-пользователей экземпляра: картинку открывает
  любой вошедший по имени файла — агент решает, что показывать, секреты и
  чужие данные на снимок не класть.
- Devin-история: `<images_input>`/`<files_input>` в реплике человека и
  блоки-картинки ACP снимаются в `message.images`/`files`
  (`readUserMessageContent`, devin-sessions.provider.ts) — раньше тег висел
  голым текстом в ленте, а сами вложения пропадали. Покрыты обе формы ввода:
  строка и массив ACP-блоков (`{type:'content',…}` разворачивается, теги в
  text-блоках снимаются так же).
- «Вернуться сюда» (devin-rewind.ts) подставляет в поле ввода текст без этих
  блоков — вложения возврат не восстанавливает, только текст; сравнение цели
  тоже идёт по тексту без тегов (лента шлёт уже чистый).

## Копирование ответа выделением (`chat/utils/copyParagraphBreaks.ts`, 25.09.26)

Пустые строки между абзацами и номера «1.», «2.» нумерованного списка браузер
в копию не кладёт: отступы и маркеры рисует CSS. Обработчик `copy` на мгновение
вставляет их в DOM и убирает до кадра. Буфер через
`clipboardData` не подменять — пропадёт жирный. Сам тег `ol` на это время
заменяется плоскими `div` с номером текстом (12.10.26): Telegram читает из
«богатой» копии `<ol>` и дорисовывает свои номера — `list-style: none` его не
останавливал, вставка давала «1. 1.». Номер берётся с экрана:
`ol.start` + `li.value`. Выделение от первой буквы пункта стоит правее вставленного номера — его начало растягивается на номер, иначе первый «1.» терялся. Компонент `ol` в `Markdown.tsx` `start` не передаёт,
поэтому список после текста и на экране, и в копии начинается с 1.

## Изоляция веб-пользователей: смотреть на КАЖДЫЙ рождающийся процесс (12.09.26)

Разделение аккаунтов делалось дважды и оба раза оказывалось неполным, потому
что проверялось только чтение данных — чьи чаты видно в списке. Но у сервера
есть второй, куда более опасный канал: процессы, которые он запускает от имени
пользователя.

Встроенный терминал (`shell-websocket.service.ts`) отдавал оболочке
`...process.env` целиком и вообще не получал опознанного пользователя —
websocket-шлюз передавал запрос чату, но не терминалу. Значит `CLAUDE_CONFIG_DIR`
был серверный, то есть общий каталог владельца площадки. Приглашённый набрал
`/login` — и OAuth-вход владельца был перезаписан чужим. Владелец при этом
увидел не ошибку, а тихую смену аккаунта; приглашённый — «CLI не
аутентифицирован», потому что интерфейс спрашивал про ЕГО каталог, где пусто.

**Правило.** Любое место, где рождается дочерний процесс (`pty.spawn`,
`child_process.*`, SDK с параметром `env`), обязано получать каталог настроек
и ключ из `shared/web-user-runtime.ts`, а не из окружения сервера. Если
пользователя определить не удалось, а `OPEN_REGISTRATION` включён — процесс не
запускается вовсе: молча писать в чужой каталог хуже, чем отказать.

**Второе правило, из той же истории.** Расчёт «чей это пользователь и куда ему
можно писать» существует ровно в одном экземпляре. Копия этого расчёта в чате
жила отдельно и не знала про терминал — та же болезнь, что у двух разошедшихся
сверок ленты сообщений в тот же день: копия отстаёт молча, и найти это можно
только по жалобе человека.

**Третий раз, 25.09.26 — «вошёл ли человек в Claude».** Терминал писал вход в
папку человека, экран «вход есть» его видел, а чат пускал не-владельца только
с ключом API из настроек (правило 02.09, до починки терминала) — вошедший
подпиской получал «Add your Anthropic API key». Теперь одна проверка:
`shared/claude-login.ts` (settings.json + `.credentials.json`; истёкший
короткий ключ при живом ключе продления = вошёл, CLI продлит сам; сервер
ключ не продлевает). Чат спрашивает `hasOwnClaudeAccess` (ключ сайта ИЛИ вход
в своей папке), отказ — `CLAUDE_LOGIN_REQUIRED` с путём «Настройки → Агенты».
Гостю процессы (чат, терминал) не получают ключи Claude из окружения сервера
(`isolateInheritedClaudeAuth`): CLI предпочёл бы их входу гостя. Тесты
сервера гонять с `env -u CLAUDE_CONFIG_DIR -u OPEN_REGISTRATION -u DATABASE_PATH`:
чат, запущенный с сайта, наследует эти переменные, и тесты входа и терминала
читают живые папки. Проба целиком — временный экземпляр (`env -i HOME=/tmp/…
DATABASE_PATH=/tmp/… OPEN_REGISTRATION=true SERVER_PORT=…`), гость по
приглашению, поддельный `.credentials.json` в его папке, `chat.send` в сокет:
«OAuth session expired» = чат пустил и CLI взял вход гостя.

## Экран входа по личной ссылке (02.10.26)

- На голом адресе сайта поле ссылки по умолчанию не показывается: основная
  кнопка читает уже скопированную ссылку через `navigator.clipboard.readText()`
  строго после нажатия человека. Буфер принимает только явный путь
  `/enter/<token>`; голый токен допустим только в ручном поле — иначе случайный
  API-ключ или номер из буфера мог бы попасть в URL и журналы.
- Ручное поле обязательно остаётся запасным путём и раскрывается по ссылке под
  кнопкой, при запрете чтения буфера или при неподходящем тексте в нём. Safari
  может потребовать отдельное системное подтверждение вставки — это нормально.
- Механика входа не дублируется в экране: оба пути только достают токен и
  переходят на существующий `/enter/<token>`, после чего работают прежние
  обмен токена, сохранение сессии и персональный PWA-манифест.
- Пока проверка `/api/auth/status` не удалась и идёт повтор
  (`statusCheckFailedAt` в AuthContext, 11.10.26), ProtectedRoute анониму
  показывает экран ожидания, а НЕ форму логина: `openRegistration` при сбое
  остаётся false-по-умолчанию и без защиты откатывал бы экран к окну
  «Добро пожаловать». Форма верна только после успешного ответа сервера.

## Чаты переживают перезапуск сайта (13.09.26)

- Агент — дочерний процесс сервера. У службы `KillMode=process` (drop-in `99-keep-agents.conf`), но этого мало: при штатной остановке SDK на `process.exit` шлёт SIGTERM всем своим детям. Проба: штатная остановка родителя — агент погиб; SIGKILL родителя — агент доделал задачу.
- Поэтому агент запускается через `spawnClaudeCodeProcess` → `survivor-runs.js`: во время остановки `kill` — пустая операция; запись `~/.cloudcli-shared/live-runs/<pid>.json` (чат, номер разговора, каталог аккаунта).
- **`live-runs` и `devin-runs` лежат рядом с базой экземпляра** (`dirname(DATABASE_PATH)`, 19.10.26), явные `CLOUDCLI_LIVE_RUNS_DIR`/`CLOUDCLI_DEVIN_RUNS_DIR` главнее. У боя база в `~/.cloudcli-shared` — пути прежние. Повод: пробная копия с базой в /tmp, но общим домом, при старте усыновила 7 живых Devin-ходов боя — бой потерял сокеты к супервизорам (`client connected (replaces previous)`), счёл ходы упавшими, и все сообщения в эти чаты падали на `session_locked` («чат ещё занят»). ## Метка работы на живых событиях (13.09.26)

`seq` у каждой работы (`chatRunRegistry.startRun`) свой и начинается с 1, а
вкладка отбрасывает события с `seq <= lastSeqRef[sid]` — защита от повторной
доставки. Счётчик был по ЧАТУ и не сбрасывался между работами: после долгой
работы вкладка помнила большой номер и молча выбрасывала ВСЕ события следующей,
включая сигналы «думает / работает». Сервер при этом считал чат занятым.

Теперь каждое событие несёт `runStartedAt` (время запуска работы), его же
возвращает `chat_subscribed`. Клиент (`chat/utils/liveRunCursor.ts`) при новой
метке обнуляет счётчик чата; подписка передаёт известную метку, и сервер при
несовпадении досылает работу с начала. Старая вкладка без метки: если её номер
больше, чем вообще есть у работы, — досылка тоже с начала.

Лента без воды. Размышления в ленте по умолчанию скрыты (`showThinking: false`
в `hooks/useUiPreferences.ts`) — и у тех, кто уже сохранил «показывать»:
одноразовая метка `uiPreferences.thinkingHiddenByDefault.v1`. Текст в размышлениях
ЕСТЬ — первое допущение «они пустые» оказалось неверным и проверялось по записи
разговора (52 блока, пустых 0). Пустые блоки дополнительно не разрывают группу
команд (`isEmptyThinking`). Свёрнутую строку вызова рисует `ToolGroupContainer`
(не `BashCommandDisplay`): в ней `description` вызова, команда — при раскрытии.
Инструмент `Agent` отображается конфигом `Task` (алиас в `getToolConfig`), иначе
падал в «Parameters».

Суб-агент приходит под именем `Task` (старое) или `Agent` (новое). Сравнивать
только через `isSubagentToolName` из `chat/tools/configs/toolConfigs.ts`: жёсткое
`=== 'Task'` в трёх местах (карточка агента, счётчик «Работают агенты», категория

Отправка без `remove` (старая сборка) — полная замена и меток не ставит: закрытия со старой сборки у новых устройств прилипают до их перезагрузки, но никого не кидают. ## Скорость: где на самом деле уходило время (замер 14.09.26)

- **Как мерить.** Каждый запрос отдельно (`curl` с `auth-token` из localStorage) даёт 3–100 мс; в браузере на этой же машине те же запросы шли 1–2,5 с. Причина не в обработчиках, а в двух ядрах, которые делят сервер, агенты чатов и проверочный Chromium. Занятость сервера мерить опросом лёгкого запроса (`/api/voice/health` раз в 200 мс): 14.09 медиана 5 мс, 95% — 22 мс, максимум 135 мс. Число запросов и вес стартовых файлов от загрузки машины не зависят, это надёжные цифры.
- **Сверка названий** (`claude-session-synchronizer`) вызывается на каждое изменение стенограммы работающего чата. Раньше читала файл целиком (89 МБ — 1,5 с процессора), теперь дочитывает хвост от последнего перевода строки (`titleScanCache`), `history.jsonl` разбирается заново только при изменении (`buildLookupMap`).
- **Повторы на клиенте.** `authenticatedFetch` склеивает одновременные одинаковые GET без тела, заголовков и сигнала отмены (каждый получает `response.clone()`). `useSlashCommands` зависит от id/пути проекта, а не от объекта. `useVoiceAvailable` держит готовый ответ минуту.
- **Стартовый файл.** `ProviderLoginModal` подключает терминал через `lazy`: цепочка ProtectedRoute → Onboarding → ProviderLoginModal → StandaloneShell → Shell затаскивала xterm в главный кусок. Проверка пути: `node ~/tmp-ccui/perf/import_path.mjs xterm` из корня репо.
- **Старт агента** (журнал `claude --debug-file`): ~3,8 с — запрос списка сервисов claude.ai (`/v1/mcp_servers`), подключение Notion/Miro 1,4–1,8 с, хуки SessionStart все вместе 0,75 с. `MCP_CONNECTION_NONBLOCKING` у CLI 2.1.270 уже включён по умолчанию.

## Лента держит место сама: `useScrollAnchor` (15.09.26)
- Жалоба: «листаю вверх — возвращает в одну и ту же точку и не даёт загрузить остальное». Замер `~/tmp-ccui/perf/scroll_snapback_probe.py <метка> <чат>` (номер первого на экране сообщения С КОНЦА должен только расти): до правки 3 отката за 150 шагов, отрезки по 10+ шагов у верха без подгрузки.

Поэтому у `.chat-messages-pane` стоит `overflow-anchor: none` — иначе Chrome вернул бы сдвиг второй раз. - Палец на стекле / инерция ПОСЛЕ КАСАНИЯ (колесо и полоса прокрутки — пишем сразу, иначе у «ложного верха» стоит до 8 шагов; TanStack PR #1280) / отскок (`scrollTop < 0`) — `scrollTop` не пишем (на iPhone обрывает бросок), сдвиг держит `margin-top: -N` у `.chat-rows`; через 140 мс без прокрутки (или `scrollend`) отступ снимается и прокрутка прибавляется в одном кадре. Приём TanStack Virtual PR #1189 / issue #1287. `scrollToBottom` и возврат на вкладку сначала сбрасывают отложенный сдвиг. Касание без движения дольше 1 с и уход приложения в фон (`visibilitychange`/`pagehide`) движением не считаются — iOS может не прислать `touchend`, и отступ висел бы.
- Порцию берём за три экрана до верха (`topPreloadMargin`); после отрисовки порции и после переноса сдвига сторож проверяется вручную (IntersectionObserver не видит нового пересечения, если сторож не выходил из зоны).

## Первое листание как второе: прогрев строк и открытие без прыжков (27.09.26)

Устройство: решение принимает чистая `decideConnectionAction`
(`src/contexts/connectionWatchdog.ts`, таблица случаев в тесте рядом) —
вынесено отдельно потому, что `WebSocketContext` живёт в React и без DOM не
проверяется, а решать судьбу связи надо проверяемо. Применяет решение
`ensureConnection` в `WebSocketContext.tsx`, вызывают её трое: сторож раз в
`CONNECTION_CHECK_MS` (5 с, на скрытой вкладке молчит), `onResume` — первым
делом, до всякой очереди, и разбор очереди — вместо прежних собственных веток
по `readyState`. Инвариант: **связь — не свойство очереди**; всё, что решает
`readyState`, живёт в одном месте. Закрытый сокет пересоздаётся даже при
назначенном повторе — именно назначенный повтор и замерзал.

глотает молча — страница не видела ни его, ни молчания замёрзшего пути:
сокет числился `OPEN`, а кадры не шли (класс «ТСПУ-заморозка»/смена сети —
`~/ccui-netwatch/journal.tsv`). Теперь сервер шлёт кадр `server_ping` раз в

тоже считается признаком жизни) → без ответа 4 с — пересоздание со сменой

## Счётчик токенов и окно «Token Usage» (23.09.26)
- Правила взяты у готовых инструментов, не придуманы. **Заполненность контекста** = `input + cache_creation + cache_read` последнего ответа ОСНОВНОЙ ветки, без вывода (документация строки состояния Claude Code; ccstatusline `jsonl-metrics.ts`; основной claudecodeui). Помощники (`isSidechain`, в живом потоке `parent_tool_use_id`), `isApiErrorMessage` и `<synthetic>` с нулевым счётом — мимо. После `compact_boundary` до нового ответа — `compactMetadata.postTokens`. **Полный расход** — сумма всех ответов, строки одного ответа склеиваются по `message.id:requestId` с максимумом по полю (ccusage, tokscale: ранние строки несут недописанный вывод).
- `provider-token-usage.service.ts`: `used` = заполненность (кнопка у поля ввода), `total` = окно, `session.*` = полный расход. Файл дочитывается с прошлого места (`scanStates`, 64 файла): первый запрос по 98 МБ ~3 с, повтор 1–15 мс.
- Окно — `claude-context-window.ts`: сообщённое Claude (`result.modelUsage[модель].contextWindow`, в итоге есть и служебный Sonnet на 200 000 — берём модель ответа), хранится в `claude-context-windows.json` рядом с базой → пометка `[1m]` у модели чата, для `default` — `model` из settings.json → виденный объём >200 000 → 1 000 000 → 200 000. Было жёсткое 160 000 при окне 1 млн.
- `/cost` спрашивает сервер сам (`dependencies.tokenUsage`), цифры браузера — только запасной путь. Причины «0» 22.09.26: главная — хранилище истории заводит `tokenUsage: null`, и каждая догрузка сообщений (у идущего чата — постоянно) ставила его в счётчик: теперь берётся только непустое; обнуление в эффекте загрузки истории после ответа сервера; запрос только при смене чата; живой `token_budget` любого работающего чата подменял цифры открытого (теперь фильтр по `sessionId`); `result.usage` (сумма хода) выдавался за заполненность.
- 11 падающих серверных проверок (claude-auth, skills, taskmaster, shell-websocket) падают и на живой версии без этой правки — не отсюда.
- **Devin** (`devin-usage.ts`, 04.10.26): usage по ACP у Devin нет — ни `usage_update`, ни `session/prompt.usage` (живые sock-журналы). Источник — его `sessions.db`: metrics каждого ответа пишутся по ходу хода. Заполненность = input+cache последнего ответа живой цепи (`main_chain_id` → parent-обход, заброшенные ветки — мимо заполненности, но в полном расходе); расход — все ответы, склейка по `request_id` (один ответ лежит парой узлов). Окно — `devin models list --format json` (кэш 10 мин), модель из `sessions.model` → `model` строки сайта → `readConfiguredDefaultModel`. Живой `token_budget` шлёт рантайм опросом базы раз в 4 с во время хода (`emitDevinTokenBudget`, повтор с тем же `used` не шлём). Симптомы до правки: endpoint отвечал `unsupported` → «0»; рантайм ставил `total=used` → «150K/150K»; `usage_update` с одним полем затирал счёт нулём.

## «Вернуться» — возврат чата к своему сообщению (26.09.26)

Фотки и скрины с iPhone приходят в .heic. Формата нет в списках картинок ни

## Самообновление открытой страницы — только в фоне (10.10.26)

`src/lib/appUpdate.ts` следит, чтобы загруженная страница не отставала от
сборки на сервере (имя `index-*.js` в `/` против загруженного) и от смены
служебного кэша (`sw:updated`). Инвариант после жалобы «сайт сам
перезагружается»: ВИДИМУЮ страницу не перезагружать никогда — под человеком
ни `ensureLatestBuild`, ни воркер, ни страховки. Политика трёх состояний:
- страница скрыта (`visibilityState === 'hidden'`) → `location.reload()`
  сразу: человек не видит, вернётся уже к новой сборке;
- страница на виду → `markUpdatePending` + событие `app:update-pending`:
  плашка «Доступно обновление» внизу панели слева, нажатие = перезагрузка
  (пропс `onApplyUpdate` в сайдбаре — больше не открывает VersionUpgradeModal,
  тот был про git pull из upstream и недостижим);
- свежее открытие страницы → перезагрузка сразу (этап загрузки, терять нечего).

`ensureLatestBuild(true)` — ветка с отсрочкой, вызывается на КАЖДЫЙ
`visibilitychange` (AppContent), не только на возврат: проверка при уходе в
фон — и есть тихий момент обновления. Защита от цикла — sessionStorage-ключ
на имя сборки (`app-update-reload-target`), пометка ожидания —
`app-update-pending-bundle`; `useVersionCheck` читает её стартовым
`updateAvailable`, поэтому плашка не пропадает при перемонтировании. Пометка
снимается двумя путями: `hasPendingUpdate` сравнивает её с именем загруженной
сборки (совпала — ожидание отработало, пометка «service-worker» сгорает на
первой новой загрузке) и `ensureLatestBuild` при совпавшей сборке шлёт
`app:update-clear` — иначе плашка висела бы и на свежей версии.
Заголовок плашки при пустых `releaseInfo/latestVersion` — «Обновить сейчас»,
не «vnull»; ключи `versionUpdate.*` лежат в `common`, поэтому в сайдбаре —
с префиксом `common:` (`t` там привязан к `['sidebar','common']`, и
непрефиксованный ключ отдаётся сырым — проба плашки поймала это 10.10).

Страница, которую не сворачивают сутками, на старой сборке не застрянет:
плашка висит, а любой уход в фон довезёт обновление сам. Черновик поля ввода
переживает перезагрузку (`draft_input_<scope>`), адрес чата — в URL.

## Пулы изменений между серверами — плашка «Обновить» (12.10.26)

Одна и та же копия приложения живёт на нескольких серверах (Егор — cc.sobsila.ru,
сотрудники — cc2 на втором). Пулы изменений ездят в обе стороны через GitHub:
- каждая сторона публикует своё состояние веткой (Егор — `origin/main` почасовым
  `ccui-publish-main.sh`; cc2 — снапшотом живого релиза в `woezix-live` форка
  Артрейда, `~/cc2/publish-live.sh`, крон */30);
- сторож `deploy/selfhost/check-updates.sh` (крон ~30 мин) сверяет работающую
  версию с источником и пишет `update-state/pending.json` (коммиты, конфликт);
- модуль `server/modules/updates` отдаёт состояние в `/api/updates/*`, а плашка
  `src/components/updates/ServerUpdateSection.tsx` (внизу сайдбара) показывает:
  «Обновить» / «Обсудить в чате» / «Отложить».

Правила, которые легко сломать:
- Состояние — файл, не запрос: сторож пишет pending.json, бэкенд только читает.
  Не делайте git fetch внутри HTTP-обработчика.
- Конфиг экземпляра — `config.json` в каталоге состояния (`applyCmd`, `repo`),
  потому что env системного юнита менять не всегда можно. env-переменные
  `CCUI_UPDATE_*` приоритетнее.
- «Обсудить» создаёт чат через `sessionsService.createAppSession` и шлёт бриф
  серверной очередью (queueChatMessage + dispatchChatQueues) — ход стартует
  без открытой вкладки; бриф собирается в `buildDiscussPrompt`.
- Конфликт считается ДО показа кнопки, дешёвыми пробами: патч-режим — каждый
  `*.patch` из `CCUI_UPDATE_PATCH_DIR` на целевом дереве (не лёг и не снимается
  обратно = пересечение); merge-режим — сухой merge BASE←REMOTE во временном
  worktree. Пустой итог merge = источник несёт только эхо своих же изменений —
  pending.json не пишем (иначе зеркала друг друга кормят вечно).
- Кнопка «Обновить» при конфликте заблокирована без `force` — разбор только
  через чат. «Отложить» скрывает плашку до следующего id, пул остаётся.

## Devin Connection Layer — корпоративные каналы (03.10.26)

Devin — не одна машинная креда, а реестр серверных каналов `devin_connections`.
Сотрудники не логинятся в Devin сами: ход идёт через канал, который сервер
выбирает по приоритету; каждый чат прибит к линии (каталогу истории) и к автору.

- **Канал = каталог.** `xdg_data_home` строки — это XDG_DATA_HOME дочернего
  `devin acp`: внутри `<xdg>/devin/credentials.toml` (0600, каталоги 0700) и
  `<xdg>/devin/cli/sessions.db`. Креды в БД и в API не живут — только путь и
  метаданные. Кто начал чат — `sessions.initiated_by_user_id` (ставит
  createAppSession из request-контекста; наследие до Layer'а — NULL, видно
  только владельцу).
- **Линия ≠ подписка (10.10.26).** `sessions.devin_connection_id` — ЛИНИЯ:
  каталог с sessions.db чата, не меняется никогда. Платит за ход ПОДПИСКА —
  креда любого годного канала: пикер → своя креда линии → первая годная
  (`pickCredentialForLane`). Чужая креда подаётся теневым XDG
  `<connections-root>/.overlays/lane-L-cred-C` (`prepareTurnDataHome`):
  содержимое линии симлинками (запись идёт в линию), `devin/credentials.toml`
  → креда подписки; созданное процессом прямо в тени (каталоги MCP-серверов —
  они тоже пишут в XDG_DATA_HOME) при следующей сборке переезжает в линию.
  В схеме sessions.db Devin поля аккаунта нет — проверено вживую: сессия,
  начатая под mywork-djn, продолжилась под default с полной памятью.
  Выключенный канал остаётся линией (`resolveLaneForSession`, ошибка только
  если канал удалён), его креда просто не платит.
- **Фоллбэк по подпискам**: лимит Devin приходит ошибкой на `session/prompt`
  ДО вывода («Reached free model rate limit… reset… at HH:MM UTC»). Пока
  человек не увидел ни строчки хода (`run.liveOutputSent`), ход повторяется
  на следующей подписке в той же линии (новый чат — грузит уже выделенную
  сессию, второй session_created не шлётся), MAX_TURN_ATTEMPTS=4. В UI —
  статус «У текущей подписки Devin исчерпан лимит — продолжаю на другой»
  (без имени подписки: строку видит гость). `recordOutcome`: auth_failed —
  навсегда до замены креды; rate_limited — cooldown до времени сброса из
  текста Devin; без срока в тексте — 15 мин, «weekly»-квота — 6 ч, повторный
  rate limit на канале удваивает отдых (потолок 12 ч) — иначе севшая подписка
  пробовалась при каждом новом ходе и «Запускаю чат» платил лишний заход
  (16.10.26); прочее — error. Перед `session/prompt` ход шлёт `run_phase:
  thinking` — плашка меняется с «Запускаю чат» на «Думает» сразу, а не на
  первом токене (16.10.26); хронометраж фаз — `[Devin] timing чат …` в
  журнале. **Грабля:** классификатор
  искал `403`/`401` подстрокой, а в тексте лимита hex trace ID — «…c403…»
  превращал лимит в вечный auth_failed; trace ID теперь вырезается, коды — `\b`.
- **Админка**: владелец — `Settings → API` → «Devin — корпоративные каналы»
  (список, здоровье, вкл/выкл, замена креды credentials.toml целиком,
  живая проба `devin auth status`, список задач канала). API —
  `/api/providers/devin/connections*` (owner-only гейт; у гостя 403, секция
  сама скрывается). Добавление канала без кода: POST connections → POST
  /:id/credential с телом креды.
- **Посев**: если реестр пуст и есть машинная креда — она становится каналом
  «default» (xdg = общий `~/.local/share`), файлы не копируются.
- **Пикер аккаунтов (09.10.26)**: в меню сайдбара — Claude (только слоты с
  вошедшим аккаунтом: пустой слот 2 скрыт, `readOwnerSlotInfo` в user.service),
  Devin (все включённые каналы реестра, подпись — ярлык
  `devin_connections.account_email`), Codex. Выбор канала Devin →
  localStorage `selected-devin-connection` → `options.devinConnectionId` в
  `chat.send` (каждый ход) → подписка следующего ответа и в новом, и в открытом
  чате; негодная — авто-фолбэк. Почту CLI не отдаёт — ярлык ставится кнопкой
  «Ярлык» в админке (PATCH accountEmail). Список каналов в пикере — owner-only
  (403 — пункты скрыты); гостям фолбэк по подпискам работает автоматически.
- **Ошибки видны**: `canReceiveProviderEvents` для devin фильтрует по
  sessionId → initiated_by_user_id (наследие — владельцу); websocket-гейт
  `isDevinSessionForbiddenForUser` — по той же авторской проверке.
- **Service-user ключи (`cog_`) CLI отвергает** — они для REST API v3, не для
  `devin acp`. Если Devin доделает service-аккаунты для CLI — креда канала
  меняется на неё без правок кода.
- Watcher (`sessions-watcher`) и activity-sync обходят все включённые каналы;
  survivor-запись хранит `devinDataHome` — после рестарта прогресс читается
  из базы канала, не из машинного дефолта.

## Скорость: счётчик токенов с хвоста, список проектов пачкой, языки по требованию (14.10.26)

- **`token-usage` для больших стенограмм отвечает разбором хвоста** (`scanClaudeTranscriptTail` в `provider-token-usage.service.ts`): с конца файла кусками по 1 МБ (не больше 24 МБ) ищется последнее значимое событие — ответ основной ветки или граница сжатия; сравнение «что позже» — по позиции в файле. Файл ≥4 МБ без полного кэша → быстрый ответ БЕЗ `session`-итогов + фоновый полный разбор (`runScanDeduped`, один на файл). `session` отдаётся только у `complete`-состояния — потребитель читает «итогов нет» как `undefined`. Было 8–10 с на 94-МБ чате → 0,3 с. Полный и хвостовой разбор уступают цикл `setImmediate` между кусками — иначе один большой файл ставит все запросы сайта на десятки секунд.
- **Список проектов — 3 запроса на всё, не на каждую папку** (`getSessionsByProjectPathsPage` + два `count*ByProjectPaths` в `sessions.db.ts`): порции чатов нумеруются `ROW_NUMBER() OVER (PARTITION BY project_path)` с тем же отбором и порядком (перенесённые в другой блок первыми, дальше по дате). На живой базе ~110 папок: 260 мс → 6 мс, списки идентичны (сверено прогоном старого и нового SQL).
- **Стартовый граф: не тащить бочки.** `index.ts` `task-master` экспортирует и лёгкий `NextTaskBanner`, и тяжёлый `TaskMasterPanel`→`PRDEditor`→CodeMirror — импорт баннера через бочку затаскивал всё в старт (368 файлов против 229). Прямой импорт `view/NextTaskBanner`. `VersionUpgradeModal` (react-markdown) — `lazy`, как Settings. Проверка: `node ~/tmp-ccui/perf/import_path.mjs <пакет>` из корня репо.
- **i18n: только ru+en в стартовом бандле** — 9 остальных языков (~460 КБ JSON) догружаются `ensureLanguage` при выборе (`addResourceBundle` + повторный `changeLanguage` для перерисовки). Ru — язык по умолчанию, en — предохранитель fallbackLng, оба обязаны быть под рукой сразу.
- **Голосовой архив: ffmpeg гасится группой, отправка одна на файл.** `convertToVoice` запускает `nice ionice ffmpeg` через `spawn(..., {detached:true})` — таймаут execFile убивал только обёртку, сироты доделывали работу на фоне (видели 26 мин при лимите 10 и 3 копии на один файл после перезапусков). `sendRecordingOnce` делит одну отправку между publishAudio и повторной доставкой; `resumePending` пропускает файлы, чья отправка ещё летит (`inFlightSends` с флагом `done` — завершённая запись не считается «в полёте», иначе повторная доставка подписи никогда не случалась бы).

Голос: `useVoiceInput` при мгновенной смерти трека (<2 с, 0 кусков, без стопа человека) перезапускает захват сам — iOS отдаёт мёртвый микрофон после прошлой диктовки, иначе запись падала в «too-short» (Егор 15.10.26). Тап-стоп выставляет счётчик повторов в максимум — автоперезапуск не должен перечёркивать намеренную остановку.

## Выгрузка чата в файл — вся переписка потоком (17.10.26)

Файл выгрузки обязан содержать чат ОТ ПЕРВОГО сообщения (Егор: «чат должен
быть весь всегда, да может чуть дольше загрузка»). Путь «дозагрузить ленту и
сохранить видимое» обрезал длинные чаты: `fetchHistory` держит полную
историю лишь в пределах `MAX_FULL_READ_BYTES` (12 МБ) с конца стенограммы —
у чата на 70 МБ выгрузка начиналась с середины, без постановки задачи.

Поэтому выгрузка идёт отдельной точкой `GET /api/providers/sessions/:id/messages/export` — NDJSON, каждое
нормализованное сообщение пишется в ответ по мере чтения источника
(`sessionsService.streamHistory`): у Claude — `streamTranscriptLines`
(файл от первого байта кусками, потолка нет, в памяти одна строка), у
провайдеров без `streamHistory` — `fetchHistory` без предела; наследие
переведённых чатов идёт первым. Поток отличается от ленты: порядок —
порядок записи файла, без склейки действие-результат (выгрузка печатает
только текстовые реплики). Лента и кнопка «догрузить ранние» продолжают
ходить постраничным путём с теми же потолками — их не поднимать без
пересмотра бюджета памяти службы (450 МБ, инцидент OOM 09.09).

Клиент (`fetchWholeTranscript` в `ChatExportMenu`) читает поток, собирает
`NormalizedMessage[]` и гоняет через `normalizedToChatMessages` — в файле
ровно то, что показала бы лента; ошибка внутри потока приезжает маркерной
строкой `{exportError}` и откатывает выгрузку на старый путь ленты.

`ChatExportMenu` собирает имя как `<название>-гггг-мм-дд-чч-мм.<ext>`: название — то же, что в сайдбаре (`summary || name || title`, в `ChatMessagesPane`), при пустом — первая реплика пользователя; минута выгрузки обязательна (Егор: «непонятно, когда только дата»). Запретные для файлов символы схлопываются в пробел, длина названия — 60 знаков.

Формат `.md` рассчитан на пересылку другому ИИ (Егор 17.10.26): заголовок
каждого сообщения — `## <роль> · YYYY-MM-DD HH:mm` (роли `user`/`assistant`/
`error`/`tool` — модельно-однозначные метки, не «You»/«Claude»), без
HTML-тегов; сообщения разделяются `---`. HTML/PDF — для человека, там
оформление прежнее.

## Защита от тихого обрывания Devin-хода (17.10.26)

Проблема: Devin иногда останавливался после блока «Как я понял задачу» или
после промежуточного статуса («сейчас поищу / докину запросы»), не доводя
ход до ответа. С точки зрения ACP ход завершился штатно (`stopReason: end_turn`),
поэтому UI показывал неполный текст и активировал поле ввода.

Инвариант: статусный текст сам по себе не считается концом хода.

Реализация в `server/modules/providers/list/devin/devin-runtime.provider.js`:

- При `agent_message_chunk` накапливаются весь текст хода и текст после
  последнего `tool_call`; replay истории во время `session/load` в аккумуляторы
  не попадает. Вызов инструмента без последующего ответа поэтому не может
  считаться завершённым результатом.
- Ответ `session/prompt` не является барьером доставки: встречаются ACP-агенты,
  которые нарушают порядок протокола и присылают последние `session/update`
  уже после `stopReason`. Перед классификацией runtime ждёт 75 мс тишины в
  ACP-событиях, но не более 500 мс; каждое позднее событие сдвигает границу.
  Закрытие CLI после уже полученного ответа prompt во время дренажа штатно;
  до ответа prompt оно остаётся аварией. Иначе финальный ответ терялся, а
  статусный префикс запускал ложное продолжение.
- После дренажа каждого `session/prompt` проверяются `stopReason` и содержание
  накопленного за эту попытку текста (аккумуляторы сбрасываются перед
  продолжением). Эвристика вынесена в `server/shared/utils.ts`
  (`isIncompleteDevinResponse`): ход считается незавершённым, если текст
  пуст, после инструмента нет текста, хвост — явное обещание продолжить
  (включая фразы с объектом вроде «сейчас поищу информацию и вернусь»), или
  весь ответ — только блок «Как я понял задачу». Ход считается содержательным,
  если в нём есть результирующий заголовок (ответ, итог, результат, вывод,
  рекомендации, возможные улучшения, версия, готовый промпт и др.), fenced
  code block, markdown-таблица, длинный нумерованный/маркированный список
  или несколько разделов. Результатная структура имеет приоритет над
  статусным шаблоном; статусные фразы проверяются только в хвосте, чтобы
  вступление не перечёркивало дописанный ответ.
- Восстановимый обрыв (статусный финал, `max_tokens`) продолжается
  служебным prompt — до `MAX_AUTO_CONTINUES` = 2 раз; человек видит только
  строку статуса «продолжаю автоматически». ACP v1 записывает каждый prompt
  репликой пользователя, поэтому текст продолжения начинается с метки
  `DEVIN_AUTO_CONTINUE_TAG` (`server/shared/utils.ts`) — её отфильтровывают
  все места, где история Devin становится нашей лентой: `devin-sessions.provider`
  (лента истории), `devin-transcript` (экспорт в новый чат), `devin-chain`
  (учёт ходов человека — автопродолжение не «witness» и не последний ход),
  `devin-rewind` (не цель возврата), синхронизатор заголовков.
- Невосстановимые причины (`refusal`, `cancelled`, прочие) и обрыв после
  исчерпания продолжений дают `kind: 'error'` + `complete(exitCode: 1)`;
  `completed` допустим только для содержательного `end_turn`. Постоянный журнал
  `chat_runs` и `run_terminal` получают `failed` для отвергнутого неполного
  результата, поэтому переподключение не превращает его в тихий успех.

Ограничение: проверка содержания эвристическая; произвольный текст без явной
статусной формулировки нельзя надёжно отличить от краткого ответа без
структурированного terminal-state контракта со стороны агента.

## Оценки формата ответов (message-feedback, 19.10.26)

Кнопки «палец вверх / палец вниз» под ответами ассистента. Контракт перенесён
из референса `~/response-format-memory` (доки и модель там): одна оценка на
сообщение, `PUT /api/messages/{message_id}/feedback` идемпотентен — повторное
нажатие переписывает ту же строку (`ON CONFLICT`), `revision` растёт; дубль
физически невозможен, поэтому повторная доставка клика безопасна.
`DELETE /api/messages/{message_id}/feedback` — отмена оценки: повторный клик
на уже активную кнопку удаляет запись из базы, кнопки возвращаются в нейтральное
состояние. Ответ `{ message_id, deleted: bool }`. Удалённая оценка не учитывается.

- Таблица `message_feedback` (в общей auth.db, создаётся лениво репозиторием):
  `message_id PK, session_id, user_id, direction ±1, category, comment,
  domain, format_hash, revision, created_at, updated_at`. `domain` и
  `format_hash` — свойства сообщения, не голоса: повторная оценка без них их
  НЕ стирает (`COALESCE`).
- Категории дизлайка фиксированы сервером (`FEEDBACK_CATEGORIES`); дизлайк без
  категории отклоняется 400; comment ≤ 2000.
- `message_id` = `message.uuid` | `message.sourceId` | `message.id`. Важно:
  текстовые сообщения ассистента несут uuid транскрипта именно в `sourceId`
  (useChatMessages) — в `id` его ставить нельзя, от него строятся ключи ленты
  и строки бы перерисовались. Без стабильного id кнопки не рисуются; во время
  потока скрыты — id ещё может смениться.
- `domain`/`format_hash` считает КЛИЕНТ по тексту ответа
  (`src/utils/formatFingerprint.ts`) — формулы держать синхронными с
  `app/fingerprint.py` и `app/domain.py` референса, иначе снапшоты не совпадут
  с будущими выборками оптимизатора. Отличие от референса: домен там
  классифицировался по тексту запроса, здесь — по тексту ответа.
- `GET /api/messages/feedback?sessionId=` отдаёт оценки только владельцу
  сессии (фильтр user_id) — лента восстанавливает нажатое состояние кнопок;
  чтение одно на сессию для всех контролов (клиентский кэш-ключ — sessionId).
- UI: `MessageFeedbackControl` рядом с MessageCopyControl в строке под
  ответом; диалог причин — портал по образцу RewindConfirmDialog (не
  position-absolute от сообщения, скролл не рвётся).
